# Experiment 2: Requirement Engineering & SRS

## Lab Record Header
- **Experiment Number**: 02
- **Title**: Software Requirements Engineering & SRS Documentation
- **Date**: Academic Session 2026

---

## 1. Aim
To perform comprehensive Software Requirements Engineering for the Smart Hospital Management System (SHMS), resulting in an IEEE 830-compliant Software Requirements Specification (SRS), stakeholder analysis, detailed functional and non-functional requirements, business rules, system boundary scope, and business event tables.

---

## 2. Objectives
1. Formulate a structured IEEE 830 SRS document for SHMS.
2. Identify primary, secondary, and managerial stakeholders.
3. Elaborate 30 granular functional requirements (`FR-01` to `FR-30`) covering all 8 SHMS modules.
4. Define non-functional quality attributes (Performance, Security, Availability, Usability, Integrity, Auditability).
5. Formalize hospital business rules (`BR-01` to `BR-08`).
6. Detail system in-scope modules and out-of-scope boundaries.
7. Map business triggers, sources, and system responses into an Event List and Event Table.

---

## 3. Documents Created
1. `SRS.md` — IEEE 830 compliant Software Requirements Specification.
2. `stakeholders.md` — Detailed stakeholder catalog and interest analysis.
3. `functional-requirements.md` — 30 detailed functional requirement specifications.
4. `non-functional-requirements.md` — 11 non-functional quality specifications.
5. `business-rules.md` — Enterprise business constraints.
6. `scope.md` — In-scope modules and explicit boundary limits.
7. `event-list.md` — Business events categorized by trigger type.
8. `event-table.md` — Structured event response table.

---

## 4. Procedure
1. Conducted domain requirement analysis based on `Smart_Hospital_Management_System.pdf`.
2. Extracted operational scenarios for Patient Registration, OP Scheduling, Consultation, Lab Tests, Pharmacy, IP Admission, Billing, and Administration.
3. Standardized requirement schemas with IDs, Names, Descriptions, Actors, Preconditions, and Expected Outcomes.
4. Categorized events into External, Temporal, and State events.

---

## 5. Result
A rigorous, complete Software Requirements Specification and event model for SHMS were established, providing 100% requirements coverage for subsequent UML modeling experiments.

---

## 6. Conclusion
Experiment 2 provides the authoritative requirements baseline essential for use case modeling, domain analysis, interaction design, and verification.
